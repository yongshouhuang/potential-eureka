# S2 垂直切片手感 Playtest 计划（Vertical Slice Feel Playtest）

> 编制：质量负责人 严守真（quality-lead）
> 配套：`production/qa/qa-plan-s2.md`（§4 为本计划缩略，本文为可独立执行的完整版）
> 引擎：Godot 4.3 LTS｜双端：PC 横屏 ≥1024 / 移动竖屏 <768｜评审：solo/lean
> 前提：用户本地已装 Godot 4.3 + GUT（见 qa-plan-s2.md §2）。**C-3 未装则连 headless 都跑不了，手感层更需真机。**

---

## 0. 为什么需要"手感"层

GUT（headless 逻辑）与 Python 算法门禁（155/155）只回答一个问题：**"核心循环能不能跑通？"**
它们抓不到第二个问题：**"核心循环好不好玩？"**

垂直切片（Vertical Slice）的 QA 目标，是验证一条**端到端可玩闭环**在真实交互下是否产生"心流"——而不只是数值正确。本计划把闭环拆成 5 个阶段，区分"逻辑已证"与"手感待验"。

```
抽卡 → 养成(升级/突破/觉醒/分支) → 组队(4式神+1法宝) → 推图(普通关→Boss关) → 资源回流
```

---

## 1. 两层验证模型

| 层 | 验证内容 | 已证？ | 工具 | 说明 |
|---|---|---|---|---|
| **Headless 逻辑层** | 养成聚合→最终式神→战斗结算→五行克制→羁绊→回流→云冲突 的数学正确性 | ✅ **已证** | Python 155/155（s2-python-logic-smoke.py） | 无需重跑；只证明"能跑通" |
| **Hands-on 手感层** | 心流节奏 / 克制反馈 / 羁绊横幅 / 双端布局 / 数值成长爽感 / Boss 张力 | ❌ **待跑** | 本地 Godot 实跑 + 本清单 | 证明"好玩吗" |

> 原则：逻辑层出问题 → 阻塞（Bug）。手感层出问题 → 多为设计调优（CONCERNS），不立即阻塞但必须记录。

## 2. 闭环入口场景（Entry Scenarios）

按"新玩家首次体验"顺序设计 5 个入口，覆盖完整闭环。每个场景给出**前置**、**操作**、**观察点**。

### 场景 A · 新档起手（首通最小闭环）
- **前置**：新存档（或 `SaveManager` 清空）；进入主菜单。
- **操作**：主菜单 →（若抽卡 UI 在 S2 切片内）抽 1 次 → 编队 4 式神 +1 法宝 → 第1章第1关 → 自动/手动打完 → 看结算。
- **观察点**：从进入到首关结算的顺畅度；回流资源是否**即时可见**（顶栏数字跳动 / 弹窗）。
- **逻辑层已证**：`test_deck_builder`（编队）、`test_battle_flow`（首关）、`E4-S5` Python（回流）。

### 场景 B · 养成深度（战力成长可见性）
- **前置**：选 1 个已拥有式神（建议 `ssr_qing_long`，真实 `shikigami_defs` 存在）。
- **操作**：
  1. 升级 ×N（耗 ling_qi）→ 看 final_stats 变化；
  2. 突破 ×3（耗 po_dan + 碎片）→ 看阶数 + 被动槽；
  3. 觉醒（达 bt3）→ 看 `awakened_skills` 标记；
  4. 分支选剑修/体修 → 看 `branch` 与被动入列；
  5. 带该式神**重进同一关**，对比战前/战后 DPS。
- **观察点**：每一步成长是否在 UI **可感知**（数字/阶位/技能图标变化）；养成前后实战差距是否"爽"。
- **逻辑层已证**：`test_cultivation.gd` 全部（T7）。
- ⚠️ **已知缺口**：觉醒的"灼烧叠层"机制（E3-S3 AC2）**未实现**，此处仅能看到技能标记，看不到叠层战斗效果 → 记为 B2。

### 场景 C · 羁绊编队（连携反馈）
- **前置**：拥有剑宗 4 人（`ssr_qing_long`/`ssr_bai_hu`/`sr_you_ming`/`sr_xuan_feng`，真实 defs 均存在）。
- **操作**：组 4 人剑宗队 → 进战斗 → 观察 `bond:combo` 触发。
- **观察点**：横幅是否出现、加成数值是否可辨、与编队（2 人 vs 3+ 人）是否匹配（预期 +8~12% / +15~20%）。
- **逻辑层已证**：`test_bond.gd`（T6）+ `test_battle_flow` 中 `get_bond_bonus` 经事件。
- ⚠️ 横幅**UI** 未被 GUT 覆盖（§3.3），此处需人工确认视觉。

### 场景 D · Boss 张力（章节收口）
- **前置**：推到第1章第9关（Boss：`c1_boss` 480hp / `c1_boss_add` 240hp，真实 chapters.json）。
- **操作**：进 Boss 关 → 打完 → 看结算回流（Boss 关符箓 2–4、突破丹 1、觉醒石 1）。
- **观察点**：Boss 血量/攻击是否带来**压力**；克制/羁绊能否**扭转**战局；通关回流是否有"收获"反馈；单场时长是否在 2–4min。
- **逻辑层已证**：`test_battle_flow::test_clear_chapter_advances_progression_and_refunds` + Python `E4-S5`/`DATA_INTEGRITY`（真实 3×9、Boss 奖励）。

### 场景 E · 双端对比（布局/热区）
- **前置**：同一存档；分别用 PC 横屏（≥1024，如 1280×720）与 移动竖屏（<768，如 390×844 模拟）运行。
- **操作**：各跑一遍场景 A–D 的"编队 + 进战斗"片段。
- **观察点**：≥1024 多栏不破版；<768 单列/仅关键数值；技能按钮热区 ≥44×44 可点；五行形状冗余（圆/三角/方/菱/五边）在灰阶下可辨。
- **逻辑层已证**：`test_battle_ui_constants.gd`（常量）+ Python `E4_S6_suite`（真实表）。
- ⚠️ **真实 HUD/热区/渲染 UI 全缺 GUT 测试**（§3.3），此处必须真机核验。

## 3. 手感检查清单（6 维度 · Checklist）

逐项勾选；任一项"否/弱"记 CONCERNS，崩溃/错误记 FAIL。

### 3.1 心流节奏（Flow）
- [ ] 单场战斗时长落在 **2–4min**（场景 D 计时）。
- [ ] 操作无卡顿/无空窗（回合间无"等死"长停顿）。
- [ ] 奖励即时可见（结算/顶栏数字变化 <0.5s 内反馈）。
- [ ] 无死锁（全员阵亡/满员时正确分胜负，不卡在等待输入）。

### 3.2 克制反馈（Element Feedback）
- [ ] 克制命中出现「克制！」浮字，且为**图标+数字+颜色三重**（Basic D）。
- [ ] 克制（×1.25–1.35）与被克（×0.7–0.8）的**伤害差肉眼可辨**（预期 ≥25% 差距）。
- [ ] 相生（×1.02–1.05）有轻微正向反馈但不喧宾夺主。

### 3.3 羁绊横幅（Bond Banner）
- [ ] `bond:combo` 触发时横幅出现且不被遮挡。
- [ ] 横幅显示的加成数值与编队匹配（2 人 vs 3+ 人）。
- [ ] 横幅出现时机与"组队触发"一致，不延迟/不漏。

### 3.4 双端布局（Dual-layout）
- [ ] PC ≥1024：多栏布局不破版、不溢出。
- [ ] 移动 <768：单列 / 仅留关键数值，不拥挤。
- [ ] 技能按钮热区 **≥44×44px** 可点（移动端手指误触率低）。
- [ ] 五行形状冗余（圆/三角/方/菱/五边）在**灰阶**下仍可区分（色盲友好）。

### 3.5 数值成长爽感（Progression Feel）
- [ ] 升级（+2.5%/级）、突破（+10%/阶）的战力提升在实战**可感知**（场景 B 前后 DPS 对比）。
- [ ] 觉醒/分支带来**质变感**（不止数字，有视觉/机制变化）。
- [ ] 资源消耗（灵气/突破丹/碎片）与产出（推图回流）节奏匹配，不出现"卡死无产出"断流。

### 3.6 Boss 战张力（Boss Tension）
- [ ] Boss 血量/攻击制造**压力**（非秒杀、非磨血无聊）。
- [ ] 克制/羁绊策略可**扭转**战局（有"操作/编队影响结果"的反馈）。
- [ ] 通关回流（符箓/丹/石）有明确"收获"反馈（场景 D）。

## 4. 观察指标（量化 Metrics）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 单关耗时 | 2–4min | 场景 D 计时 |
| 克制 vs 被克 平均伤害差 | ≥25% | 同阵容分别打克制/被克目标，取均值比 |
| 羁绊触发率 | 100%（满足条件的编队） | 场景 C 观察横幅出现次数/应出现次数 |
| 双端断点 | 0 溢出 / 0 裁切 | 场景 E 截图比对 ≥1024 与 <768 |
| 热区点击命中率 | ≥95%（移动端 ≥44px 按钮） | 场景 E 连续点击 20 次统计误触 |
| 养成前后 DPS 提升 | 升级/突破可量化（如 bt0 Lv1 → bt3 Lv11 实测 DPS 差） | 场景 B 同关同敌对比 |
| 回流到账视觉延迟 | <0.5s | 场景 A/D 结算到顶栏跳动计时 |

## 5. 通过 / 不通过标准（Pass / Fail Criteria）

### PASS（可放行体验）
- 闭环 5 阶段**完整走通**，无崩溃/死锁。
- §3 的 6 维度**全部"可感知且正确"**。
- 双端（≥1024 / <768）**均不破版**、热区可点。
- 单场时长落在 2–4min 预算内。

### CONCERNS（不阻塞，记设计调优）
- 闭环可走通，但某维度"**不够爽**"（如成长感弱、反馈弱、Boss 偏易/偏磨）。
- 处置：记入 `production/qa/bugs/`，交 design-strategist 调数值/反馈，不阻塞 S2 门禁。

### FAIL（阻塞，必须修）
- 任一核心环节**崩溃 / 死锁 / 数值明显错误**（例：克制反被克伤害更高、回流扣减而非增加）。
- 双端**严重破版**（布局溢出导致无法操作、热区不可点）。
- 单场时长**严重超标**（>6min 或 <30s 无内容）。
- 处置：开 Bug，回 engineering-lead 修复后重跑本 Playtest。

## 6. 执行前置与责任

1. **前置依赖**：用户本地装 Godot 4.3 + GUT（qa-plan-s2.md §2）。C-3 未装 → 本手感层无法启动（连 headless 验证都没有）。
2. **执行人**：solo/lean 评审下由主理人或指定体验官按本清单实跑；QA 负责人回收勾选结果并判定 PASS/CONCERNS/FAIL。
3. **产出**：勾选后的清单 + 双端截图 + 时长/伤害记录，回填至 `production/qa/` 作为 S2 体验证据。
4. **与 GUT 互补**：本 Playtest 不替代 GUT（逻辑断言），GUT 也不替代本 Playtest（体验）。两者在 S3 收口时须**同时绿**。
